# 双通知源外壳与独立配置分区

## Status

accepted

## Context

项目原本只服务 Nacos：托盘、主窗口、设置、通知都围绕服务实例展开。现在要以「Tray Notify Tool」的形态同时承载 Nacos 与 Jenkins，两类对象没有共同字段（实例 vs 构建任务），配置与通知节奏也完全不同。用户明确要求 Nacos 与 Jenkins 的连接、行为、备注各自独立、互不影响。

## Decision

1. 采用「薄外壳」：托盘、设置面板、主题、通知中心由两个来源共享；Nacos 现有轮询与主窗口逻辑保持不动，Jenkins 作为第二个来源接入，不抽象通用插件框架。
2. 配置按来源分区：`config.json` 内新增 `nacos`、`jenkins` 两个对象，界面配置（主题、视图、快捷键等）仍留在顶层；旧版扁平配置在首次启动时自动迁移。
3. 备注与免打扰按来源命名空间存储：`notes.json` / `dnd.json` 内分为 `nacos` 与 `jenkins`，旧扁平格式自动迁移。
4. Jenkins 运行状态单独存 `jenkins_state.json`，只记录基线、已通知构建号与已展示提交，不写入配置。
5. 设置面板侧边栏分两组：通知源（Nacos、Jenkins，各自含连接、行为、备注）与通用（常规、外观、快捷键、关于）；通用组新增「常规」承载开机自启这类应用级设置。
6. 主窗口顶部提供来源切换，一次显示一个来源；Nacos 保持表格/卡片，Jenkins 本期只做表格。
7. 托盘右键弹窗左右等宽两栏：左栏 Nacos、右栏 Jenkins，两栏等高、各自滚动；未配置 Jenkins 时右栏隐藏。
8. 应用更名 Tray Notify Tool，版本 v2.0；配置目录迁移到 `.tray-notify`（保留旧目录），开机自启注册表值改为 `TrayNotify` 并清理旧值。

## Considered Options

- 定义通用 `NotificationSource` 接口并迁移 Nacos：为两个来源引入插件层，改动面大、收益低。
- 拆成两个独立托盘程序：用户明确要一个统一工具，且会占用两个托盘图标。
- 配置继续扁平、用前缀区分：字段无命名空间，迁移和校验都容易出错。

## Consequences

- 设置窗口页面从 6 个增加到 9 个，需要分组侧边栏承载。
- 旧版配置只保证单向迁移到新目录，回退旧版本不会读取新配置。
- 两个来源各自拥有独立线程与错误边界，一个来源失败不影响另一个。
