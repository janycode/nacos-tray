# Jenkins 以构建开始与结束作为通知事件

## Status

accepted

## Context

参考实现（help-memory-system 的 `JenkinsMonitorService`）只监控配置过的 Job、只在构建成功时推送企业微信，且通过本地 git 仓库补提交日志。托盘工具需要在没有本地仓库、没有企业微信的前提下，让用户知道构建何时开始、何时结束，以及这次构建带来了哪些新提交。

## Decision

1. 认证使用用户名 + 密码的 Basic Auth 逐次请求，不引入会话登录或自动生成 API Token；连接页只填地址、账号、密码，密码支持显示切换。
2. 递归展开文件夹与多分支，只监控叶子 Job；包含/排除两个过滤框按完整 Job 路径做不区分大小写的匹配，排除优先。
3. 事件只有两类：构建开始（首次观察到某构建号且 `building` 为真）与构建结束（构建完成）；结束结果只分为成功与失败，非成功一律视为失败。短构建若在两次轮询之间完成，只发结束通知，不补发开始。
4. 首次观察某个 Job、或过滤规则变更后新入选的 Job，只静默建立基线，不通知。
5. 构建结束通知包含：项目名、构建号、开始时间、结束时间、总用时、分支（从构建参数 `BRANCH_NAME` 或包含 `BRANCH` 的参数提取）、本次新提交；开始通知只包含项目名、构建号、开始时间、分支。
6. 提交来自 Jenkins 构建的 `changeSet`；按参考实现规则筛选：最新两条无条件保留，其余只保留 `feat/fix/docs/style/refactor/perf/test/build/ci/chore/revert` 前缀、排除 merge，最多展示 5 条，超出显示「等 N 条」。按 commit id 与该 Job 已通知提交对比去重，无新提交则不显示提交段；开始通知不带提交。
7. 轮询失败时首次弹一条警告，连续失败不重复；恢复时弹一条恢复提示；失败期间保留已有基线，只有成功拉到 Job 列表的轮询才裁剪已删除 Job 的状态。
8. Jenkins 行为页提供「通知构建开始 / 构建成功 / 构建失败」三个开关，轮询间隔默认 30 秒、最小 10 秒。

## Considered Options

- 沿用参考实现的白名单 + 只报成功：无法满足「全量感知 + 开始/结束」的诉求。
- 会话登录拿 JSESSIONID：形式上更像登录，但受 CSRF 与 SSO 影响，跨 Jenkins 版本易碎。
- 只用本地 git 日志取提交：需要为每个 Job 配置本地目录，且与构建实际使用的提交可能不一致。
- 不通知成功、只通知失败：用户明确要求成功与失败都要知道。

## Consequences

- 流水线 Job 的 `changeSet` 可能为空，此时结束通知没有提交段；后续如有需要再补本地仓库兜底。
- 全量 Job 在繁忙 Jenkins 上通知量较大，依赖过滤框与三个行为开关降噪。
- 10 秒以内的短构建可能没有开始通知，这是轮询模型无法避免的。
